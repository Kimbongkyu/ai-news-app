# 뉴스 수집기 기능 개발 워크플로
뉴스 수집기 앱에서 새 기능을 개발할 때 브랜치 생성부터 커밋·병합까지 순서대로 진행합니다.
브랜치 이름 : $ARGUMENTS

## 실행 순서

### 1. 현재 상태 확인
- `git status`와 `git branch --show-current`로 현재 상태를 확인해 줘.
- 현재 브랜치가 master가 아니면 경고하고, master로 이동할지 사용자에게 물어봐. 사용자가 동의하기 전에는 이동하지 마.
- 커밋되지 않은 변경이 있으면 함께 알려 주고, 어떻게 할지 사용자에게 물어봐. 임의로 stash하거나 버리지 마.

### 2. 새 브랜치 만들기
- $ARGUMENTS가 있으면 그 이름으로 브랜치를 만들고 이동해 줘.
- $ARGUMENTS가 비어 있으면 어떤 기능을 개발할 것인지 사용자에게 물어봐. 답을 받으면 영어 소문자-하이픈 형식(예: `category-admin`, `notion-save`)으로 브랜치 이름을 제안하고, 사용자가 확인하면 그 이름으로 만들어 줘.

### 3. 개발 시작 안내
- 브랜치 생성이 끝나면 '이제 개발을 시작하세요!'라고 안내해 줘.
- CLAUDE.md를 읽고 이 프로젝트의 기술 스택과 컨벤션을 다시 한번 요약해서 알려 줘. 최소한 다음을 포함해:
  - 기술 스택 (Next.js, React, TypeScript, Tailwind, Clerk, Neon + Drizzle, OpenAI, Notion 등 CLAUDE.md 기준)
  - Next.js 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 관련 가이드를 읽을 것
  - UI를 만들거나 수정하기 전에 ui.md를 읽을 것
  - 기능 범위는 PRD.md가 기준이며, 미결정 사항은 임의로 정하지 말고 사용자에게 확인할 것
- 이후 사용자가 요청하는 개발 작업을 진행해. 사용자가 '완료' 또는 'done'을 입력하기 전에는 4단계로 넘어가지 마.

### 4. 완료 처리 (사용자가 '완료' 또는 'done'을 입력했을 때)
- `git status`와 `git diff --stat`으로 변경된 파일 목록을 보여 줘.
- 변경 내용을 바탕으로 커밋 메시지를 자동으로 제안해 줘. 기존 커밋 메시지(`git log`)의 한국어 스타일을 따라.
- 사용자가 확인하기 전에는 커밋하지 마. 수정을 요청하면 반영해서 다시 제안해.
- 사용자가 확인하면 변경 파일을 커밋하고(`.env*` 같은 비밀 파일은 제외), master로 이동해 이 브랜치를 병합해 줘 (`git merge --no-ff`).
- 병합 중 충돌이 나면 멈추고 충돌 파일을 알려 준 뒤 사용자에게 어떻게 할지 물어봐.
- push는 사용자가 따로 요청하지 않으면 하지 마.

### 5. 작업 요약
- 병합이 끝나면 작업 내용을 요약해서 보여 줘:
  - 브랜치 이름과 커밋 해시
  - 변경된 파일과 핵심 변경 내용
  - 병합 결과 (현재 브랜치, 최신 커밋)
  - 후속으로 할 일이 있으면 함께 알려 줘 (문서 갱신, 환경변수 추가, DB 변경 등)
